# 코드 리뷰 규칙

모든 변경은 PR로 `main`에 들어가며, 병합 전에 리뷰를 받습니다.
사람 리뷰어와 AI 리뷰어 모두 이 문서를 기준으로 봅니다.

## PR 작성자

- PR 제목은 커밋 메시지 형식(`feat: ...`, `fix: ...`)으로 씁니다. squash merge 시 이 제목이 커밋이 됩니다.
- PR 템플릿의 체크리스트를 채웁니다: 무엇을/왜, 관련 이슈, 테스트 방법, 화면 변경 시 스크린샷.
- PR은 작게 유지합니다. 파일 400줄 이상 변경이면 나눌 수 있는지 먼저 검토합니다.
- 리뷰 요청 전에 직접 확인합니다:
  ```bash
  python -m unittest discover -s tests
  ```

## 리뷰 우선순위

위에서부터 중요합니다. 위 항목에 문제가 있으면 아래 항목(스타일 등)보다 먼저 지적합니다.

### 1. 증거 무결성 (차단 사유)

- 원본 증거(하이브, E01, 로그, 사용자 파일)를 **쓰기 모드로 열거나 수정·삭제하지 않는지**.
  추출·복구는 항상 별도 작업 폴더의 사본에서 합니다.
- 분석 전후 SHA-256 비교, `image_manifest.json`의 원래 경로·해시 기록이 유지되는지.
- 추출 파일 덮어쓰기 금지(`"xb"` 모드, 비어 있지 않은 출력 폴더 거부)가 유지되는지.
- 증거에서 나온 명령행·스크립트를 **실행하지 않는지**.

### 2. 해석의 정확성 (차단 사유)

- 시각의 의미(`time_field`)가 정확한지. 예: BAM은 "마지막 실행", Run 키는 "키 수정 시각"이지
  실행 시각이 아닙니다. 모르면 `None`으로 둡니다. 추측한 값을 사실처럼 저장하지 않습니다.
- 파일 이름만 같은 관계를 "실행 확인"처럼 단정하지 않는지(신뢰도 라벨 사용).
- 손상된 입력에서 예외로 전체 분석이 멈추지 않고, `ParserError`로 기록 후 다음 입력을 계속 처리하는지.
- 바이너리 파싱 시 길이·오프셋 경계 검사가 있는지(잘린 파일, 순환 링크, 음수 크기).

### 3. 보안

- HTML 보고서에 증거 문자열을 넣을 때 이스케이프하는지(`html.escape`, `_script_json`).
- CSV 내보내기의 수식 주입 방지가 유지되는지.
- 경로 조합 시 증거 속 파일 이름이 출력 폴더 밖으로 나가지 않는지(`_safe`).
- 관리자 권한 사용은 사용자가 명시적으로 선택한 경우(UAC 확인)에만.

### 4. 사용자 표시 문구

- GUI·보고서에 보이는 이름은 `log_hunter/core/labels.py`를 거친 **쉬운 한국어**인지.
  BAM, Prefetch 같은 전문 용어는 설명(`ARTIFACT_DESCRIPTIONS`)에만 괄호로 둡니다.
- CSV/JSON/SQLite의 내부 키(`bam`, `prefetch`, `key_lastwrite`)는 바꾸지 않습니다.
- 오류 메시지는 사용자가 다음에 무엇을 하면 되는지 알려 주는지.

### 5. 테스트

- 새 파서·기능에는 합성 바이너리로 만든 테스트가 있는지(실제 증거 파일은 저장소에 넣지 않음).
- 새 샘플·고정 파일·스크린샷이 생성 코드로 다시 만들어지고(`example/**`, `tests/fixtures/**`), 가짜 값만 쓰며,
  크기 제한(파일 10MB, `example` 50MB) 안인지. 실제 PC 출력·사건 자료·외부 공개 샘플이 섞이지 않았는지.
- 버그 수정에는 그 버그를 재현하는 테스트가 있는지.
- 외부 패키지 없이 `python -m unittest`로 돌아가는지.

### 6. 코드 품질

- 런타임 Python 의존성 0개 원칙(`pyproject.toml`의 `dependencies = []`)을 지키는지.
- 주변 코드와 같은 스타일(짧은 함수, 모듈 docstring 한 줄, 과하지 않은 주석)인지.
- 새 파서는 `ArtifactParser`를 상속하고 `PARSERS`(pipeline.py), `labels.py`, 자동 감지,
  필요하면 `image/extract.py`의 `ARTIFACT_SPECS`에 등록되었는지.
- 참고한 외부 포렌식 도구의 이름·코드·데이터·문구가 들어오지 않았는지. 기능만 참고해 새로 작성해야 합니다
  (코드·문서·화면 문구·파일 이름·커밋 메시지 모두).

## 리뷰 코멘트 형식

코멘트 앞에 심각도를 붙입니다.

| 접두어 | 의미 | 병합 |
| --- | --- | --- |
| `[차단]` | 증거 무결성·해석 오류·보안·테스트 실패 | 고치기 전 병합 불가 |
| `[제안]` | 더 나은 구현, 누락된 경계 처리 | 작성자가 판단, 답변 필요 |
| `[사소]` | 이름, 오타, 스타일 | 선택 |
| `[질문]` | 의도 확인 | 답변 필요 |

- 문제와 함께 **구체적인 실패 상황**(어떤 입력에서 무엇이 잘못되는지)과 가능하면 수정안을 적습니다.
- 확인하지 않은 추측은 `[질문]`으로 씁니다.

- 리뷰 코멘트는 `[내 이름] 리뷰:`로 시작하고, 승인은 **`[내 이름] 리뷰: 승인`** 코멘트로 표시합니다(같은 계정이라 GitHub Approve 기능은 쓰지 않음).

## 병합 조건

[에이전트 협업 규칙 6절](agents.md#6-서로-리뷰하고-스스로-병합)을 따릅니다. 요약:

- 다른 에이전트의 `리뷰: 승인`이 마지막 커밋 이후에 있음(단독 모드는 `자체 리뷰: 승인 (단독 모드)`)
- `[차단]`·`[질문]` 모두 해결
- 전체 테스트 통과, `python tools/check_confidential.py range origin/main..HEAD` 통과
- 공용 규칙·설정 파일 PR은 대리 승인까지
- PR 작성자가 squash merge, 병합 후 브랜치 삭제

# 이슈 규칙

GitHub Issues로 버그와 기능 요청을 관리합니다. 이슈를 만들 때는
`.github/ISSUE_TEMPLATE`의 템플릿을 사용합니다.

## 종류와 라벨

| 템플릿 | 제목 형식 | 라벨 | 작업 브랜치 |
| --- | --- | --- | --- |
| 버그·오류 (`issue.md`) | `[issue] <무엇이 잘못되는지>` | `issue` | `issue/<번호>-<설명>` |
| 기능 요청 (`feat.md`) | `[feat] <무엇을 하고 싶은지>` | `feat` | `feat/<설명>` |

추가 라벨(선택): `parser`(아티팩트 파서), `image`(E01/NTFS/이 PC 분석), `ui`(GUI·보고서),
`docs`, `good first issue`.

## 에이전트 라벨

에이전트끼리·사용자와 에이전트 사이의 일은 아래 라벨로 주고받습니다([에이전트 협업 규칙 4절](agents.md#4-작업-표시와-소통)).

| 라벨 | 뜻 |
| --- | --- |
| `from:claude1`·`from:codex1` | 쓴 에이전트 |
| `to:claude1`·`to:codex1`·`to:user` | 처리할 대상(`to:user`는 대부분 claude1이 대리 승인) |
| `agent:request`·`agent:question`·`agent:blocker`·`agent:info` | 요청·질문·막힘·알림 |
| `in-progress`·`blocked` | 진행 상태 |

에이전트가 쓰는 이슈·코멘트는 맨 앞에 `[이름]`을 붙입니다. 이름 표시가 없으면 사용자가 쓴 글입니다.

## 좋은 이슈의 조건

- **재현 가능해야 합니다.** 버그는 입력 종류(E01, dd, 하이브 직접 추가, 이 PC 분석),
  기록 종류(예: 최근 실행한 프로그램/BAM), 실행 방법(GUI/CLI 명령), 실제 결과와 기대 결과를 적습니다.
- **오류 메시지는 전체를 붙입니다.** GUI의 "처리 결과/오류" 탭 내용이나 CLI 출력, traceback.
- **환경을 적습니다.** Windows 버전, Python 버전, 관리자 권한 여부.
- 한 이슈에는 한 가지 문제만 적습니다.

## 증거 데이터 주의 (중요)

- **실제 사건의 증거 파일, 하이브, E01을 이슈에 첨부하지 않습니다.** 사용자명, SID,
  파일 경로, IP 등 개인 정보는 가립니다(`S-1-5-21-xxx-1001`, `C:\Users\<user>\...`).
- 재현용 파일이 필요하면 테스트 VM에서 새로 만든 샘플이나, `tests/`처럼 코드로 만든
  합성 데이터를 사용합니다.

## 처리 흐름

1. 이슈 생성 → 라벨 지정
2. 담당자가 브랜치 생성: `issue/<번호>-<설명>` 또는 `feat/<설명>`
3. PR 본문에 `Fixes #번호`(버그) / `Closes #번호`(기능)
4. PR 병합 시 이슈 자동 종료

버그를 고칠 때는 **그 버그를 재현하는 테스트를 먼저 추가**하고, 테스트가 실패하는 것을
확인한 뒤 수정합니다.

# 에이전트 협업 규칙 (claude1 · codex1)

이 저장소에서는 AI 에이전트 **claude1(Claude Code)** 과 **codex1(OpenAI Codex CLI)** 이 동시에 작업합니다.
두 에이전트는 서로의 대화 내용을 모르므로, 협업은 **GitHub(브랜치·이슈·PR)와 이 문서**로만 합니다.
사용자의 직접 지시가 항상 이 문서보다 우선합니다.

## 1. 내가 누구인지

- **내 이름은 `git config --get agent.name`** 으로 확인합니다. 작업 폴더를 만든 사람이 처음에
  `python tools/setup_agent.py <이름>` 으로 정해 둡니다(이 작업 폴더에만 저장, 커밋되지 않음).
- 값이 비어 있으면 작업 전에 사용자에게 묻고, 직접 정하지 않습니다.
- **작업 방식은 `git config --get agent.mode`** 로 확인합니다: 비어 있거나 `team`이면 협업 모드(2~9절), `solo`이면 단독 모드(10절).
  사용자가 채팅으로 단독 모드를 지정·해제하면 그 지시를 따릅니다.

## 2. 작업 공간은 따로

두 에이전트는 **서로 다른 폴더(git worktree)** 에서 작업합니다. 폴더는 모두 같은 상위 폴더(`Documents\GitHub`) 아래에 둡니다.

| 폴더 | 누가 |
| --- | --- |
| `Log_Hunter` (원본 클론) | **사용자 전용.** 에이전트는 여기서 파일을 고치거나 브랜치를 바꾸지 않습니다 |
| `log-hunter-claude` | claude1 |
| `log-hunter-codex` | codex1 |

- 만드는 법(원본 폴더에서 사용자가 한 번):
  ```bash
  git worktree add --detach ../log-hunter-claude origin/main
  git worktree add --detach ../log-hunter-codex origin/main
  ```
  그다음 각 폴더에서 `python tools/setup_agent.py claude1` / `codex1` 실행, `.confidential-terms`를 비공개 경로로 받아 폴더 맨 위에 둡니다.
- 다른 에이전트의 작업 폴더에 들어가 파일을 읽거나 고치지 않습니다. 상대 작업은 GitHub의 브랜치·PR로만 봅니다.
- 개인 작업 기록(진행 상황, 초안, 검증 로그)은 각자 폴더의 `outputs/<내 이름>/`(git 무시)에 둡니다.
  세션이 끊겨도 이어서 하도록 `outputs/<내 이름>/progress.md`에 "현재 / 다음 할 일 / 완료 / 보류 / 이슈 확인 기록"을 유지합니다.

## 3. 담당 영역

| 영역 | 담당 | 경로 |
| --- | --- | --- |
| 화면(GUI)·트리·콘텐츠 뷰어·속성 창, 보고서(HTML), 사용자 문서, 예제 해설 문서 | **claude1** | `log_hunter/ui/`, `log_hunter/core/tree.py`, `log_hunter/core/report.py`, `docs/` (dev 제외), `README.md` |
| 분석 엔진: 파서, 자동 인식, 이미지·NTFS·볼륨 섀도 복사본, 이 PC 읽기·수집, 상관 분석, 저장·DB, 성능, 설치·빌드 | **codex1** | `log_hunter/parser/`, `log_hunter/image/`, `log_hunter/collector/`, `log_hunter/database/`, `log_hunter/core/`(tree·report 제외), `log_hunter/main.py`, `tools/build_pyz.py`, `example/`, `internal/`, `pyproject.toml`, `*.bat` |
| 함께 쓰는 파일 | 수정한 쪽이 상대에게 알림 | `log_hunter/core/labels.py`(항목은 파일 끝이 아니라 관련 사전 안에 추가), `tests/` (각자 자기 영역 테스트) |
| 공용 규칙·설정 | 대리 승인(9절) 후 한 에이전트만 | `docs/dev/*`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `.github/*`, `.claude/*`, `.codex/*`, `tools/setup_agent.py` |
| 비공개 자료 검사 장치 | **사용자만** | `tools/check_confidential.py`, `tools/hooks/*` |

- 상대 담당 경로의 파일은 고치지 않습니다. 필요하면 이슈나 PR 코멘트로 요청합니다.
- 새 아티팩트처럼 엔진·화면에 걸친 일은 엔진(codex1)이 먼저 데이터 형식(필드 이름)을 이슈에 확정하고, 화면(claude1)은 그 형식으로 작업합니다.
  형식이 정해지기 전에는 형식과 무관한 부분부터 합니다.

## 4. 작업 표시와 소통

- 이슈 제목, PR 제목, 이슈·PR 코멘트, 사용자에게 하는 보고의 **맨 앞**에 `[내 이름]`(예: `[codex1]`)을 붙입니다.
  두 에이전트와 사용자가 같은 GitHub 계정을 쓰므로, **이름 표시가 없는 글은 사용자가 쓴 것**으로 보고 가장 먼저 처리합니다.
- PR 본문 첫 줄은 `작업자: <이름>`, 커밋 본문 마지막 줄은 `Agent: <이름>`.
- 에이전트끼리는 **GitHub 이슈**로 소통합니다. 라벨(`python tools/setup_agent.py <이름> --labels`로 생성):
  - 보낸 쪽 `from:<이름>`, 받는 쪽 `to:<이름>`·`to:user`
  - 종류 `agent:question`·`agent:request`·`agent:blocker`·`agent:info`
  - 이슈 성격 `feat`·`issue`(이슈 규칙), 상태 `in-progress`·`blocked`
- 사용자가 에이전트에게 일을 맡길 때는 `to:<이름>` + `agent:request` 이슈(또는 채팅)로 맡깁니다.
- **받은 이슈 확인**: 세션 시작 직후, 커밋·푸시할 때마다(최소 커밋 3개마다), 작업 단위가 끝날 때, 세션을 끝내기 전에
  `gh issue list --label "to:<내 이름>" --state open`과 라벨 없는 새 이슈, 내 PR의 충돌·리뷰 코멘트를 확인하고
  착수하면 `[내 이름] 확인, <계획>` 코멘트 + `in-progress`. 확인할 때마다 progress.md에 한 줄 기록합니다.
- 우선순위: ① 사용자 글(이름 표시 없음) ② 내 PR의 충돌·`[차단]` 리뷰 ③ 상대의 `agent:question`·`agent:blocker` ④ 받은 `agent:request` ⑤ 내 백로그.
- 결정이 필요하면 `to:user` 이슈를 엽니다. 대부분은 **claude1이 사용자 대신 결정**합니다(9절). 결정 전까지 그 부분은 추측으로 진행하지 않고 다른 일을 합니다.
- 질문을 보낸 뒤 답을 기다리며 멈추지 않습니다. 합리적인 기본값으로 진행하고 그 결정을 함께 적습니다.

## 5. 충돌 막기

1. 시작 전에 `git fetch`, `gh pr list`, `git branch -r`로 겹치는 작업이 있는지 봅니다.
2. 다른 에이전트의 브랜치에 커밋·푸시하지 않습니다.
3. 브랜치는 [브랜치 규칙](branch-rules.md)대로 `feat/<설명>`, `issue/<번호>-<설명>`. **PR base는 항상 `main`** — 다른 작업 브랜치 위에 쌓은 PR을 만들지 않습니다
   (base 브랜치가 먼저 병합되면 변경이 `main`에 들어가지 않는 사고가 있었습니다). 앞 PR이 필요하면 병합을 기다립니다.
4. 공용 파일(`labels.py`, `pipeline.py`, `tree.py`, README)에 항목을 더할 때는 파일 끝이 아니라 관련 사전·절 안에 넣습니다.
   내 PR이 열려 있는 동안 `main`이 같은 파일을 바꾸면 `git merge origin/main`으로 미리 합칩니다(rebase·force-push 금지).
5. 충돌이 나면: 서로 다른 항목을 더한 충돌은 **둘 다 남기고**, 의미가 겹치면 `main` 동작을 유지하는 쪽으로 합친 뒤 PR에 근거를 적습니다.
   생성되는 파일(예제 출력·해설판)은 손으로 섞지 말고 생성기로 다시 만듭니다. 상대 PR의 충돌은 고치지 않고 알림 코멘트만 남깁니다.
6. 공용 규칙 문서는 대리 승인(9절) 없이 고치지 않습니다.

## 6. 서로 리뷰하고 스스로 병합

PR은 사용자를 기다리지 않고 에이전트끼리 리뷰해서 병합합니다.

1. **리뷰:** 작성자가 아닌 **다른 에이전트**가 [코드 리뷰 규칙](code-review.md)대로 리뷰합니다(claude1 ↔ codex1).
   PR 코멘트로 남기고 `[내 이름] 리뷰:`로 시작합니다. 같은 GitHub 계정이라 "Approve" 기능은 쓰지 않고(`gh pr review` 금지),
   승인은 코멘트 **`[내 이름] 리뷰: 승인`** 으로 표시합니다. 고칠 점은 `[차단]`/`[제안]`/`[사소]`/`[질문]`.
   가능하면 별도 임시 worktree에서 그 PR을 받아 테스트를 직접 돌려 근거를 남깁니다.
2. **병합 조건 (모두 충족):**
   - 다른 에이전트의 `리뷰: 승인`이 **마지막 커밋 이후에** 달려 있다(승인 뒤 커밋을 더 올리면 다시 승인)
   - 해결되지 않은 `[차단]`·`[질문]`이 없다
   - `python -m unittest discover -s tests` 통과, `python tools/check_confidential.py range origin/main..HEAD` 통과
   - PR 제목·본문·코멘트에 참고 자료 이름·경로·개인정보가 없다(직접 확인, [비공개 자료 규칙](confidentiality.md))
   - 이 PR과 관련된 `to:user` 이슈가 열려 있지 않다
3. **병합 방법:** PR **작성자**가 `gh pr merge <번호> --squash --delete-branch`. 병합 뒤 상대에게 영향이 있으면 `agent:info` 이슈로 알립니다.
4. **공용 규칙·설정 파일 PR**은 리뷰 승인에 더해 **대리 승인(9절)** 이 있어야 병합합니다. 보통 codex1 리뷰 + claude1 대리 승인,
   claude1이 작성자면 codex1이 리뷰와 대리 승인을 함께 합니다. 비공개 자료 검사 장치를 바꾸는 PR은 **사용자만** 병합합니다.
5. 상대가 오래 응답하지 않아도 자기 PR을 스스로 승인·병합하지 않습니다(단독 모드 제외). `to:user` 이슈로 알립니다.
6. **초안(draft) PR**: 테스트가 남았거나 덜 끝났으면 `--draft`, 본문 맨 위에 `미완: <남은 일>`. 완료 기준을 채우면 `gh pr ready` +
   `[내 이름] 리뷰 준비 완료: 테스트 N개 통과` 코멘트. 세션 시작마다 내 초안부터 확인해 이어 갑니다.

## 7. 이슈 닫기와 브랜치 정리

- **이슈 닫기**: 기본은 PR 병합(`Fixes #n`/`Closes #n`)으로 닫힙니다. 직접 닫을 때는 근거(병합 PR·커밋, 재현 명령과 결과)를 먼저 코멘트합니다.
  사용자가 쓴 이슈는 수정이 `main`에 병합됐거나 사용자가 닫으라고 했을 때만 닫습니다. 병합 전 PR이 있는 이슈, 상대가 진행 중인 이슈는 닫지 않습니다.
  닫기 전에 `gh issue view <n> --comments`로 마지막 코멘트를 다시 확인합니다.
- **브랜치 정리**: 내 브랜치만, PR이 MERGED이고 변경이 `origin/main`에 실제로 들어 있으며(조상 확인 또는 merge commit 확인) 미푸시 커밋이 없고
  다른 PR의 base가 아닐 때만 정리합니다(`--delete-branch`로 병합하면 원격은 자동 삭제). `main`, 열린 PR 브랜치, 상대 브랜치, stash는 지우지 않습니다.
- **동기화 점검**(작업 단위마다): 원격에 없는 커밋(`git log --branches --not --remotes`), PR 없는 브랜치, 충돌 중인 내 PR,
  병합됐는데 `main`에 없는 PR(base가 main이 아니었던 경우)을 찾아 처리합니다.

## 8. 비공개 자료와 데이터

- [비공개 자료 규칙](confidentiality.md): 참고한 외부 도구·저장소의 이름·경로·코드·데이터·문구와 개인정보를 커밋·PR·이슈·문서에 남기지 않습니다.
  커밋 훅과 `tools/check_confidential.py`가 막습니다. 훅을 끄거나 우회(`--no-verify`)하지 않습니다.
- [데이터 규칙](data-policy.md): 예제·테스트·스크린샷은 코드로 만든 가짜 데이터만. 실제 PC·사건 데이터는 커밋하지 않습니다.

## 9. 사용자 대리 승인 (claude1)

사용자를 기다리지 않고 진행하도록, **claude1이 사용자 대신 결정·승인**합니다.

1. **claude1이 대신 정하는 것:** `to:user` 이슈의 질문과 결정(설계 선택, 우선순위, 담당 조정, 공용 규칙 문서 변경 승인), 공용 규칙·설정 파일 PR의 병합 승인.
2. **방법:** 해당 이슈·PR에 `[claude1] 대리 승인: <결정과 이유>`. claude1 자신이 요청한 결정이거나 claude1이 작성한 공용 규칙 PR이면
   스스로 승인하지 않고 **codex1이 `[codex1] 대리 승인:`** 으로 결정합니다.
3. **확인 시점:** claude1은 리뷰·병합을 돌 때마다 `gh issue list --label "to:user" --state open`도 확인합니다.
4. **대리 승인할 수 없는 것 (사용자만):** 저장소 공개 범위·설정·협업자·브랜치 보호·삭제, 라이선스 결정, 비용이 드는 일,
   비공개 자료 검사 장치와 비공개 낱말 목록 변경, 비밀 정보(토큰) 생성·변경, 실제 사건 증거를 다루는 일, 기록 재작성·force-push.
5. 대리 승인한 결정은 사용자가 나중에 뒤집을 수 있습니다.

## 10. 단독 모드 (solo)

사용자가 한 에이전트에게 단독 모드를 지정하면(채팅 지시, 또는 `python tools/setup_agent.py <이름> --solo`로 `agent.mode=solo`)
이 절이 담당 구분(3절)·교차 리뷰(6절)·대리 승인(9절)보다 우선합니다. 단독 모드 에이전트는 다른 에이전트를 기다리지 않고 전체 영역을 맡습니다.

- 작업 단위마다 브랜치 → PR → **자체 리뷰** → squash merge. 다른 에이전트가 남긴 열린 PR 브랜치도 이어서 고칠 수 있습니다(작성 기록은 PR 코멘트로).
- 병합 전 점검 순서: 증거 무결성 → 해석 정확성 → 보안 → 표시 문구 → 테스트 → 품질([코드 리뷰 규칙](code-review.md)).
  전체 unittest와 `check_confidential.py range origin/main..HEAD` 통과, PR 제목·본문·코멘트에 참고 자료 이름·경로·개인정보 없음.
- PR에 `[내 이름] 자체 리뷰: 승인 (단독 모드)` + 검증 결과·미검증 항목을 남기고 `gh pr merge <n> --squash --delete-branch`.
- 공용 규칙·일반 결정은 `[내 이름] 대리 승인 (단독 모드): <결정과 이유>`로 승인합니다.
- 9절 4항(사용자만 하는 일)은 단독 모드에서도 하지 않고 다른 일을 계속합니다. 훅 우회·force-push·`main` 직접 푸시 금지, 실행 정책 차단은 우회하지 않고 보고합니다.
- 진행과 문제는 사용자가 정한 채널로 보고합니다(기본: 채팅 보고, 이슈는 기록용).
- 다른 에이전트의 작업 폴더는 여전히 건드리지 않습니다. 사용자가 단독 모드를 해제하면(`--team`) 협업 규칙으로 돌아갑니다.

## 11. 사용량 한도까지 이어서 일할 때

- 작업은 작게 나눠 자주 커밋·푸시합니다(끊겨도 남게). 막히면 이유를 progress.md "보류"에 적고 다음 일로 넘어갑니다.
- 한도가 가까워 보이면 새 단위를 시작하지 않고, 테스트 통과 상태로 커밋·푸시·초안 PR(`미완:`), progress.md "다음 할 일"을 구체적으로 남깁니다.
- 큰 파일 전체 출력·긴 로그 출력을 피합니다(필요한 부분만 읽기).
